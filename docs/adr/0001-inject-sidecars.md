# ADR-0001 prepare / publish サイドカーはコントローラが注入する

- **status**: accepted（2026-08-30）
- **根拠**: issue #73 / PR #74。先行事例と実測は PR 本文に

**決定**: verdict の回収プロトコルの Pod 側の端（`out/` を敷く init と、SIGTERM で封じて
termination log に書くネイティブサイドカー）は、コントローラが Job 生成時に注入する。
handler が書くのは `spec.workspace: {volume, mountPath}` だけで、サイドカーの存在を知らなくてよい。

- 注入コンテナの uid はコントローラが選ぶ（template が名乗る uid を避けて 65532 から下へ）。
  handler 作者に「この uid を使うな」を課さない。宣言ディレクトリは 0777 で、fsGroup 合わせも不要
- handler に残る条件は 2 つ: Pod の `securityContext.runAsUser` を書く（未設定だとイメージ既定で
  見えず、違う uid を選べない）/ 少なくとも 1 コンテナが workspace を書き込み可でマウントする
  （無ければ沈黙が確定しているのに実行時まで気付かない）。どちらも配管が定義できるための条件
- **root で走る handler は拒否しない。** それは Pod セキュリティポリシーの層で、
  コントローラはポリシーを持たない（P2）。uid 分離が守る相手はエージェント（操られうる側）であって
  handler 作者ではない
- 注入コンテナへ渡す env（store 認証情報）の口は、消費者ができる段（store 封印）で足す

**覆したもの**: 2026-08-25 の「`spec.workspace` はコントローラに消費者が無いので置かない」。
判定の回収は §2 でコントローラの責務であり、P7 が排除するのはプロンプト・モデル・API キー・store。
サイドカーは LLM を知らないので対象外だった。線引きは「タスクに関することか」— 何を実行するか・
どの権限で・どのプロンプトで、は利用者。判定をどう回収するかは配管。

**覆すには**: 注入の形では表現できない handler（複数 workspace、注入側にも subPath が要る
PVC backend 等）が実際に出て、`spec.workspace` の拡張で吸収できないと分かること。
