# ADR-0003 subPath 無しのマウントは「この run」を見せ、残骸は次の run の prepare が明示リストで掃除する

- **status**: accepted（2026-09-02、人間の承認）
- **根拠**: issue #85。ADR-0002 の利用側の台本（cnp-check 報告フェーズ）を書いて見つかった 2 点

**決定**:

1. **flow-workspace のマウントは、subPath を書かなければ readOnly でも「この run のビュー」**
   （生成時に literal `subPath: work/<runID>` を焼く）。棚（封印済み run の一覧）が欲しいマウント
   だけが `subPath: results` と明示する。ADR-0002 の「readOnly には焼かない」だと、自分の run を
   読むだけのサイドカー（cnp-check の notify）が root を見せられ、runID を env で引き込む写経 —
   この設計が書き込み側から消したもの — が読み取り側で復活していた。規則は
   「黙っていれば自分の run、棚が欲しければ棚と言う」
2. **残骸掃除**: prepare は work/ を 1 階層上でマウントして自分の run ディレクトリを作り
   （kubelet の subPath 機構任せをやめてモードを自分で選ぶ）、**コントローラが計算した sweep
   リスト**にある `work/<id>` を消す。何が生きているかを知るのはコントローラだけなので、
   消してよい対象の判断はクラスタの状態が見える側に置き、prepare は言われたものを消すだけ。
   直列の今はリスト = 自 runID 未満の全部（封印済みは rename で work/ に居ないので、実際に
   消えるのは封印できず死んだ run の残骸だけ）。並列化の日はコントローラのリスト計算だけが変わる
3. **消せなければエラー**（fail-closed）。NFS のゴースト（sillyrename）等で削除が通らないのは
   ボリュームが係争中ということで、その上で新しい仕事を始めない — prepare 失敗 → infra retry →
   上限で Escalated。掃除自身はリトライ機構を持たない（次の run が再試行そのもの）
4. **Escalated で止まった Task の残骸は残る**。掃除は次の run の prepare しか走らせないので、
   人間が呼ばれるケースでは書きかけが検死素材として TTL まで残る、という非対称が構造から出る

**覆したもの**: ADR-0002 決定 5 の「readOnly 側にはコントローラは何も焼かない」と、
同「掃除を持たない（残骸は Task の TTL で PVC ごと消える）」の暗黙の前提。後者は「消して困る
データは制御上存在しない」（run N+1 が始まった時点で N の verdict の受理経路は閉じている）ことを
確認した上での改訂

**覆すには**: 並列 run で「subPath 無し = この run」の一意性が崩れる設計が出たとき（その場合も
先に壊れるのは sweep でなくビューの意味論）。掃除の対象を results/ に広げたくなったら、それは
棚の寿命の話で別 ADR

**未解決**: sweep の実クラスタ実測（NFS ゴースト時に ENOTEMPTY で prepare が落ち、Escalated まで
届くか）— ADR-0002 の実測リストに合流
