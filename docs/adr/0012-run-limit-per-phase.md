# ADR-0012 循環の上限は、フェーズごとの実行回数で数える

- **status**: accepted（2026-09-24、人間の承認）
- **根拠**: issue #160。並列フェーズ（#159）の規則を詰めていて、既存の予算の数え方が並列と両立しないと分かった

**決定**:

1. **flow は `maxRunsPerPhase`（既定 1、最小 1）を宣言する。** 遷移先のフェーズが、このタスクで既にその回数
   走っていたら、遷移せず `Escalated`（outcome `RunLimitReached`）。上限は遷移**先**に掛かる — まだ走って
   いないフェーズへの前進は常に通り、終端は走らないので終端への到達も止めない
2. **数えるのはフェーズの run。handler でも辺でもない。** 同じ handler を複数フェーズに束縛するのは正当な
   使い方で（§4「同一 handler の複数フェーズ束縛を禁止」を却下した理由と同じ）、それぞれが flow の別の場所。
   辺を数えると、次の「覆したもの」の二重取りが起きる
3. **回数は history から導く。** status に残数を持たない（`status.reworkBudget` は消す）。走行中の run は
   history に無いが走っているので 1 と数える — これで自己ループも上限に掛かる。インフラ再試行は history に
   載らないので数えない（ADR-0004 と同じ線）
4. **既に走ったフェーズへの遷移は outcome `Rework` として残すが、何も消費しない。** 後ろへ行ったという
   事実の記録であって、上限の判定には関わらない
5. **上限 1 未満が遷移に届いたら `Failed`（`Structural`）。** スキーマの最小値と既定で届かないはずだが、
   届いたら「どのフェーズも走れない flow」で、それは仕事が回数を使い切ったのではなく定義の欠陥

**覆したもの**: design.md §5「予算消費は宣言させず、実行時に判定する」の規則 —「遷移先が訪問済みなら
`reworkBudget` を 1 減らす、0 なら `Escalated`」。

- **差し戻した後の前進でも引かれていた。** `実装 → レビュー → 実装` で 1、そこから `レビュー` へ前進すると
  レビューも訪問済みなのでもう 1。1 周で 2 消費し、周が長いほど多く引かれる。数字から「何周できるか」が
  読めなかった
- **並列フェーズと両立しない。** 並列の枝が 1 本の予算を奪い合うと、最後の 1 をどの枝が使い、どの枝が
  `Escalated` に倒れるかが、枝の終わった順で変わる。同じ入力で結果が変わるのは、この framework が式を
  拒んでまで守っている「実行前に検証できる」（P9）に反する。フェーズごとの回数なら、並列の枝は互いに素な
  フェーズを持つので、判定が枝ごとに閉じて順序に依存しない

移行: `reworkBudget: 0` と `maxRunsPerPhase: 1` は同じ挙動（どちらも「一度も後戻りしない」）。
`reworkBudget: N`（N ≥ 1）には対応する値が無い — 周の長さで意味が変わっていたので、flow ごとに
「各フェーズを何回まで走らせたいか」を決め直す。

**却下した案**:

- **DFS の後退辺だけを rework とみなして予算を引く**（辺の分類を admission で静的に決める）。二重取りは
  消えるが、どの辺が後退辺かは探索順で変わりうるので、作者が読んで分かる規則にならない。並列の奪い合いも
  消えない
- **並列の枝ごとに予算を配る**。flow に数字をもう 1 つ書かせ、領域ごとに訪問済みを消す規則が要る。
  フェーズごとの回数なら何も足さずに同じ性質が出る
- **フェーズごとの上限を束縛ごとに書かせる**（`bindings[x].maxRuns`）。書くのは数値で式ではないので P9 には
  反しないが、今は消費者がいない。要るようになったら flow の値の上書きとして足す（既存の flow は壊れない）

**覆すには**: 1 つのフェーズの run を、その run の中身によって数えたり数えなかったりしたい場面が出たとき
（例: 変化の無かった再実行を数えない）。それは run の中身をコントローラが読むことで、P4 / P7 の側から
もう一度決め直す

**未解決**: 入れ子の循環では、内側で使った回数が外側の周で戻らない（後の周ほど内側の余裕が減る）。
「そのフェーズに使う回数の総量」と読めば正しい挙動で、戻す規則を足す方が複雑になると判断したが、
実際の flow で困るかは入れ子の循環を持つ flow がまだ無いので未確認
